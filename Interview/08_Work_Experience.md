# 경력 기술서

## 🎯 Goal

* 경력기술서에 작성한 **실제 구현 경험을 기술적으로 설명할 수 있도록 준비한다.**
* 단순히 기능의 결과를 설명하는 것이 아니라 **구조 → 구현 방식 → 문제 → 해결 방법 → 트레이드오프**까지 설명한다.
* 면접관의 꼬리질문에 대비해 지금까지 공부한 **C++, 자료구조/알고리즘, 객체지향, 디자인 패턴, Unity/C# 등의 이론을 실제 경험과 연결**한다.
* 직접 구현하지 않은 기술은 직접 경험한 것처럼 말하지 않고, **이론적으로 알고 있는 부분과 실제 구현 범위를 명확하게 구분한다.**
* 같은 내용을 반복하는 질문은 제거하고, 하나의 질문에서 자연스럽게 이어질 수 있는 기술적인 꼬리질문까지 준비한다.

# 1. 전투 시스템

## Q1. Hit Reaction 시스템을 어떻게 구현했나요?

### 키워드

- Animation Sequence
- AttackData
  - 피격 방향
- 애니메이션 전환

### 답변

Animation Sequence Event를 통해 `AttackData`가 포함된 Collider를 소환하고, Projectile도 같은 방식으로 처리했습니다.

이후 Collider에 피격되면 `AttackData`에 설정된 공격 방향 정보를 확인해서 `Hit_R`, `Hit_L` 같은 방향별 피격 애니메이션을 재생하도록 구현했습니다.

### 꼬리질문

* AttackData를 Collider에 전달한 이유는 무엇인가요?
* 공격 방향을 판단할 때 어떤 기준으로 방향을 결정할 수 있나요?
* Collider 충돌과 실제 데미지 판정을 분리한다면 어떤 구조가 좋을까요?
* 여러 공격 타입을 하나의 AttackData로 처리할 때 어떤 장점이 있나요?
* 공격 데이터가 많아졌을 때 객체지향적으로 어떻게 관리하는 것이 좋을까요?
* Event 기반 구조와 Update에서 직접 판정하는 방식의 차이는 무엇인가요?

## Q2. Grab 시스템에서는 공격자와 피격자의 위치를 어떻게 맞췄나요?

### 키워드

- Grab Bone
- LateUpdate
  - 위치 보간

### 답변

Grab 클래스에 공격자와 피격자의 Grab Bone을 각각 지정하고, 두 Bone의 위치를 기준으로 캐릭터의 위치를 보간했습니다.

이 보정은 `LateUpdate`에서 처리해서 애니메이션에 따른 Bone 위치를 반영하면서 공격자와 피격자의 위치가 자연스럽게 맞도록 구현했습니다.

### 꼬리질문

* 왜 `Update`가 아니라 `LateUpdate`에서 처리했나요?
* Animation 업데이트와 Script의 Update 순서는 어떻게 되나요?
* 위치를 단순히 대입하지 않고 보간한 이유는 무엇인가요?
* `Lerp`와 `MoveTowards`의 차이는 무엇인가요?
* Grab Bone을 기준으로 위치를 보정할 때 Rotation까지 보정한다면 무엇을 고려해야 하나요?
* 여러 프레임에 걸쳐 Transform을 계속 보정할 때 발생할 수 있는 문제는 무엇인가요?

## Q3. Airborne 시스템은 어떤 방식으로 구현했나요?

### 키워드

- Knockdown 재사용
- FixedUpdate
- 반복 피격
  - 중력 / 상승력

### 답변

피격자가 공중에 뜨는 상황에서는 Knockdown 애니메이션을 활용해 누워 있는 상태와 일어나는 상태를 처리했습니다.

물리적인 Rigidbody를 직접 사용하는 대신, 내부 `FixedUpdate`에서 힘을 적용하는 방식으로 이동을 계산했습니다. 중력이 적용된다고 가정하고 현재 높이를 계산해서 상승과 하강을 처리했습니다.

공중에서 다시 피격되는 경우에는 Airborne을 다시 적용하되, 반복해서 너무 높이 튀는 것을 방지하기 위해 두 번째 피격부터는 위로 올리는 힘을 줄였습니다.

바닥에 떨어진 이후에는 일정 시간이 지나면 일어나는 애니메이션을 재생하고 정상 상태로 복귀하도록 처리했습니다.

별도의 Airborne 전용 애니메이션을 추가하지 않고 기존 Knockdown 애니메이션을 활용한 것은 리소스 추가를 줄이기 위한 판단이었습니다.

### 꼬리질문

* 왜 Rigidbody를 사용하지 않았나요?
* `FixedUpdate`와 `Update`의 차이는 무엇인가요?
* 물리 기반 이동에서 FixedUpdate를 사용하는 이유는 무엇인가요?
* 중력을 코드로 계산한다면 속도와 위치를 어떤 순서로 갱신해야 하나요?
* 반복 피격 시 상승력을 줄이는 이유는 무엇인가요?
* Rigidbody 방식과 직접 물리 계산 방식의 장단점은 무엇인가요?
* Animation과 물리 이동을 동시에 처리할 때 발생할 수 있는 충돌 문제는 무엇인가요?

## Q4. Combo / Random Attack 시스템에서는 여러 공격 패턴을 어떻게 처리했나요?

### 키워드

- AttackData
  - Combo
  - Random
- Animation 다양화

### 답변

일반 공격을 반복하다 보니 몬스터의 공격 패턴이 획일적으로 보인다는 기획 의견이 있어서 개선했습니다.

하나의 Attack에 여러 `AttackData`를 등록하고, `next attack`이 지정되어 있고 다음 State도 Attack이라면 Combo 공격으로 판단해 지정된 다음 공격을 이어서 실행하도록 했습니다.

Combo가 아닌 경우에는 Attack List에 등록된 공격 중 하나를 Random으로 선택해 실행하도록 구성했습니다.

공격 데이터 자체가 매번 달라지는 구조라기보다는 동일한 공격 데이터를 사용하면서 여러 애니메이션을 선택할 수 있도록 구성해 시각적인 공격 패턴을 다양화했습니다.

### 꼬리질문

* Random으로 공격을 선택할 때 완전히 동일한 확률로 선택해야 하나요?
* 특정 공격이 연속으로 선택되는 것을 방지하려면 어떻게 할 수 있나요?
* Combo와 Random 선택을 State Machine에서 어떻게 구분할 수 있나요?
* 공격 종류가 많아졌을 때 switch문이 계속 증가한다면 어떻게 개선할 수 있나요?
* 상태 패턴과 데이터 기반 설계의 차이는 무엇인가요?

## Q5. 전투 시스템에서 AttackData를 별도의 데이터로 관리한 이유는 무엇인가요?

### 키워드

- Data / Logic 분리
- 재사용성
- 객체 책임
- 결합도

### 답변

AttackData는 공격에 필요한 데이터만 제공하는 역할이기 때문에 MonoBehaviour일 필요가 없다고 생각합니다.

공격자 쪽에서 해당 데이터를 설정하고, 피격자 쪽에서는 전달받은 AttackData를 읽어서 필요한 피격 처리를 하는 구조로 이해하고 있습니다.

제가 직접 설계한 부분은 아니지만 이런 식으로 공격 데이터와 실제 동작을 분리하면 데이터를 재사용하기 쉽다는 장점이 있다고 볼 수 있습니다.

### 꼬리질문

* MonoBehaviour가 아닌 일반 C# Class로 데이터를 관리하는 장점은 무엇인가요?
* 데이터와 로직을 분리하면 어떤 장점이 있나요?
* 객체지향에서 단일 책임 원칙(SRP)과 연결해서 설명할 수 있나요?
* AttackData를 ScriptableObject로 관리한다면 어떤 장점이 있을까요?
* 데이터 중심 설계와 객체 중심 설계의 차이는 무엇인가요?

# 2. Game AI

## Q1. Boss AI는 어떤 구조로 구현했나요?

### 키워드

- FSM
- GameState
- Phase 전환
  - Skill 조건 (ex. HP)

### 답변

Boss AI는 기존 `AIBase`를 기반으로 하되, 기존 Update와 FSM 구조는 Boss의 Phase 구성에 맞게 수정했습니다. Phase는 Boss의 HP를 기준으로 나눴습니다.

1Phase에서는 기존 AIBase의 FSM 로직을 사용하고, 2Phase에서는 스토리 진행과 특수 UI를 보여주면서 카메라 시점을 변경했습니다. 당시 플레이어가 포탑을 타는 연출이 있어서 FPS처럼 1인칭 슈팅 방식으로 전투가 진행되도록 별도의 처리를 했습니다.

3Phase에서는 다시 기존 AIBase 기반 FSM으로 돌아가도록 구성했으며, 특정 스킬은 HP가 일정 비율 이하일 때 사용할 수 있도록 조건을 추가했습니다.

### 꼬리질문

* FSM을 사용했을 때 장점과 단점은 무엇인가요?
* Boss Phase를 FSM State로 처리하지 않고 별도의 Phase 시스템으로 분리한 이유는 무엇인가요?
* HP 조건과 State 조건이 동시에 존재한다면 우선순위를 어떻게 관리해야 하나요?
* FSM State가 많아졌을 때 State Explosion 문제를 어떻게 해결할 수 있나요?
* FSM과 Behavior Tree의 차이는 무엇인가요?
* AI의 Update 비용을 줄이기 위해 어떤 방법을 사용할 수 있나요?

## Q2. 기존 AIBase의 FSM 구조를 Boss의 Phase 시스템에 적용하면서 가장 크게 변경한 부분은 무엇인가요?

또한 Phase2에서는 Boss의 스킬이 거리와 관계없이 플레이어에게 적용되는 연출이었기 때문에 일반적인 거리 기반 스킬 판정과 다르게 처리했습니다.

## Q3. Auto Play AI는 어떤 방식으로 플레이어의 다음 행동을 결정하고 이동하도록 구현했나요?

### 키워드

- Spawner 순차 진행
  - Trigger
- Quest
  - NPC
  - Dungeon

### 답변

초기에는 던전을 구역별로 순차 진행하는 구조였기 때문에 각 구역에 배치된 Spawner를 순서대로 목표로 지정했습니다.

플레이어가 Spawner의 Trigger를 밟으면 해당 구역의 전투가 진행되고, 전투가 끝나면 다음 Spawner를 목표로 지정하는 방식이었습니다.

이후 Quest 시스템이 도입되면서 일반 맵과 던전의 진행 방식이 나뉘었습니다. 일반 맵에서는 Quest NPC를 다음 목표로 지정하고, Quest를 받은 이후에는 해당 Quest와 연결된 던전 입구를 목표로 지정하도록 변경했습니다.

던전에서는 기존처럼 Spawner를 순차적으로 진행하도록 처리했습니다.

### 꼬리질문

* 순차적인 목표 관리를 List나 Queue로 구현한다면 각각 어떤 차이가 있나요?
* 목표가 중간에 추가되거나 삭제된다면 어떤 자료구조가 적합할까요?
* Auto Play 중 플레이어가 직접 조작하면 어떤 우선순위로 처리해야 하나요?
* Trigger 기반 진행 방식과 State 기반 진행 방식의 차이는 무엇인가요?

## Q4. NPC Roaming AI는 어떤 방식으로 구현했나요?

### 키워드

- Waypoint
- State

### 답변

Level에 빈 GameObject를 이동 지점으로 배치하고 NPC마다 이동 순서에 맞춰 해당 지점들을 할당했습니다.

NPC Type이 Roaming인 경우 현재 지점에서 다음 지점으로 순차적으로 이동하도록 구현했습니다.

각 지점에 도착하면 해당 지점에서 잠시 Idle 상태로 있을지 바로 다음 지점으로 이동할지를 Random으로 결정하도록 했습니다.

플레이어가 NPC에게 대화를 걸면 Roaming을 중단하고 Dialog를 진행하며, 대화가 끝나면 다시 Roaming을 시작하도록 처리했습니다.

### 꼬리질문

* Waypoint를 배열과 List 중 어떤 자료구조로 관리할 수 있나요?
* Roaming State와 Idle State를 FSM으로 구성한다면 어떻게 나눌 수 있나요?
* Dialogue 중 Roaming을 중단할 때 State를 어떻게 관리하는 것이 좋을까요?
* NPC가 많아졌을 때 모든 NPC가 매 프레임 이동 판단을 하면 어떤 문제가 발생할 수 있나요?

# 3. Animation Sequence Editor

## Q1. Animation Sequence Editor를 직접 개발하게 된 이유는 무엇이었나요?

### 키워드

- Animation/Event 분리
  - 리소스 중복
- Event 확장성
- Editor Tool

### 답변

처음부터 제가 필요성을 판단해서 새로 만들었다기보다는 리소스 최적화를 위해 애니메이션 데이터를 확인하는 과정에서 기존 구조의 문제를 발견하게 됐습니다.

기존에는 Animation과 Event가 결합된 구조라서 같은 Animation을 사용하더라도 Event가 달라지면 Animation 데이터가 추가로 필요했고, Event에 필요한 매개변수를 유연하게 지정하기도 어려웠습니다.

그래서 Animation과 Event를 분리하고, Animator가 이벤트를 사용할 수 있도록 관련 함수를 제공한 뒤 이를 Editor에서도 편하게 설정할 수 있도록 구현했습니다.

### 꼬리질문

* Animation과 Event를 분리하면 왜 리소스 중복이 줄어드나요?
* 데이터와 동작을 분리하는 것과 객체지향의 관심사 분리는 어떤 관계가 있나요?
* Editor Tool을 만들 때 Runtime 코드와 Editor 코드를 분리해야 하는 이유는 무엇인가요?
* Unity Editor API를 활용할 때 Runtime에 포함되지 않도록 관리하는 방법은 무엇인가요?

## Q2. Animation과 Event를 분리할 때, 각각 어떤 역할을 담당하도록 설계했나요?

### 키워드

- Legacy Animation
- Event Data
- Coroutine
- Animation Time

### 답변

Animation은 Legacy Animation을 이용해 재생 자체만 담당하도록 하고, Event는 Animation과 별도로 관리하도록 분리했습니다.

Animation의 현재 재생 시간을 Coroutine으로 확인하면서 특정 시점에 등록된 Event Method를 호출하는 방식으로 구현했습니다.

이렇게 해서 하나의 Animation을 여러 Event 구성에서 재사용할 수 있도록 했습니다.

### 꼬리질문

# 5. 최적화

## Q1. Animation 리소스 용량을 줄이기 위해 어떤 최적화를 진행했나요?

### 키워드

- Animation/Event 분리
  - 중복 리소스
- Curve
- Loading / Patch

### 답변

기존에는 Animation 파일 안에 Animation Curve와 Event가 함께 들어가 있었습니다.

Sequence System을 적용하면서 Animation과 Event를 분리하고, Animation 파일에는 실제 애니메이션에 필요한 Curve 정보만 남기도록 했습니다. Event는 별도의 Sequence 데이터로 관리했습니다.

이를 통해 동일한 Animation에 서로 다른 Event가 필요한 경우에도 Animation 파일을 추가로 만들 필요가 없어졌고, 결과적으로 Animation 리소스 용량을 줄여 로딩이나 패치 측면에서도 유리하도록 개선했습니다.

### 꼬리질문

그래서 제 코드만 확인하지 않고 몬스터의 Update 동작이나 Navigation 처리까지 전반적으로 확인했습니다.

몬스터가 생성될 때는 문제가 없었지만 많은 몬스터가 동시에 이동하기 시작하는 시점에서 1~2분 정도의 긴 지연이 발생했고, 이를 통해 Navigation 경로 탐색이 주요 원인이라고 판단했습니다.

이처럼 문제가 발생했을 때는 먼저 원인이 제 작업인지 다른 기능인지 확인하고, 제 작업이 아니라는 것이 명확하고 엔진 자체의 문제가 아니라면 해당 기능을 작업한 개발자에게 상황을 전달해서 확인을 요청합니다. 반대로 제 작업에서 발생한 문제라면 해당 부분을 직접 수정하는 방식으로 대응했습니다.
